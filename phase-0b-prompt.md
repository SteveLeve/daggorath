Carry out **Phase 0b: the executable evidence pack** for the Dungeons of Daggorath mobile preservation project. Read the project instructions and `Phase-0-Archaeology.md` before starting, especially sections 4–7, 13, and 20–22. Produce working artifacts and documented evidence, not just a plan. Do not build a mobile UI.

**Preservation requirement:** Original Mode must reproduce the original five fixed dungeon maps and historical game sequence. The assembly seeds maze generation by level; its clock-dependent RNG advance occurs _after_ maze construction. Preserve original initial populations, timed creature regeneration, RNG behavior, and event order. A seed supplied by the player or newly randomized maps belongs only in a separate future mode. If an older instruction or example implies a freely seeded Original Mode, follow this requirement.

Work in this order:

1. **Pin evidence and provenance.** Record exact commits, file hashes, tool versions, and rights information for every source, listing, emulator, and ROM used. Distinguish the reconstructed assembly listing, contemporary documentation, community ports, and an observed retail ROM. Use third-party ports as reference material; do not copy their code or assets without establishing rights. If a usable retail ROM is unavailable, continue with source-derived evidence and mark all ROM-dependent conclusions unverified.

2. **Build machine-readable fixtures.** Decode the original RNG and level seeds, all five 32×32 maze layouts, vertical features, token tables, item tables, creature definitions, and initial level populations. Specify byte order and a stable maze serialization before recording hashes. Verify that each level’s maze hash is unchanged across different entry times and repeated entries; separately record the RNG state before and after the post-maze clock-dependent advance. Give each fixture a source location and an extraction or verification method. Never invent a hash or fixture value.

3. **Specify the clock and scheduler.** Write a jiffy-by-jiffy account of interrupt order, counter rollovers, countdown queues, ready-queue insertion, task execution, keyboard polling, and command dispatch. Cover simultaneous expirations, typing while creatures act, five-minute regeneration, blocking animation and sound, and level transitions. Label each rule as source-proven, ROM-observed, inferred, or unresolved.

4. **Capture comparison traces where possible.** Use a legally available ROM and emulator to record timestamped keystrokes, clock and RNG state, task order, maze bytes, player and creature state, and relevant screen or sound events. Prioritize level entry and return at different times, the regeneration boundary, simultaneous tasks, parser edge cases, and MOVE/TURN/LOOK timing. Include repeatable capture instructions and distinguish raw observations from interpretation. If ROM tracing is blocked, document the obstacle and provide source-derived traces without presenting them as ROM validation.

5. **Implement the smallest headless C++20 reference slice.** Keep the core independent of SDL and platform APIs. Implement the original RNG, fixed level-0 maze generation, timed keyboard input and parsing needed for MOVE/TURN/LOOK, a discrete clock/scheduler sufficient for those commands, and a CLI that runs timestamped input scripts and emits comparable state/event traces. Use CMake. Add focused tests against independently derived fixtures, including the level-0 maze hash and relevant timing boundaries. Do not implement combat or broaden the core to hide unresolved timing differences.

6. **Reconcile the archaeology report.** For each investigated `VERIFY` item, record the evidence, result, confidence, and any source-versus-ROM difference. Leave unsupported claims explicitly unresolved. Update the provenance ledger and document deviations in the reference slice.

**Completion gate:** Provide the fixture files, scheduler specification, trace scripts and outputs, headless source and tests, updated archaeology report, and concise build/run instructions. Run the tests and CLI comparison, report actual results and the first divergence for any mismatch, and state precisely which claims are verified against a retail ROM versus the reconstructed source. Recommend the next implementation slice only after assessing this gate; do not expand into combat or mobile work during Phase 0b.
